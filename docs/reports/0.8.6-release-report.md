## 二、性能方法

- 同机同指纹（os|cpu|rustc|ram_gb）才计算 delta；0.8.5-rerun / 0.8.6-dev / 0.8.6 三者指纹一致（25H2 + UBR 8875）。
- 确定性语料：`benchmarks/specs/corpus.json`（seed=20260806），引擎 10k/100k 与系统 10k 夹具本次预生成一次、多版本复用，保证跨版本语料逐字节一致。
- 引擎 5 轮（warmup 2）、系统 7 轮；指标输出 p50/p90/p99/min/max/mean/CV/samples。
- 15% 警示规则：p50 变化 ≥15% 记为警示，不阻塞发布，逐项说明原因与 0.8.7 去向。

## 四、≥15% 警示与去向

| 指标 | 变化 | 原因 | 0.8.7 去向 |
| --- | --- | --- | --- |
| 引擎扫描 10k/100k | -88.8% / -90.0% | 原生 Win32 枚举落地为默认，省去每文件 metadata 调用 | 保持；MFT 在更大规模由优化器接管 |
| 首次扫描 10k | -83.9% | 同上（系统级全链路） | 保持 |
| 标签查询 | +30.0%（vs 0.8.5） | 本轮索引集收敛（移除低收益 type 索引）+ 查询噪声；相对 0.8.6-dev 已快 27% | FTS5 / 标签索引评估（`benchmarks/fts-evaluation.md`） |
| 文本查询 | -37.1%（vs 0.8.6-dev） | 查询路径与索引收敛 | 保持 |
| 前端 JS gzip 指标 | 不可比 | 旧指标取「dist 首个 JS」，分包后不稳定 | 0.8.7 改为「主包 gzip」口径 |

> 修复记录：初测发现可交互耗时 +33%，定位为默认文件页被页面级 lazy 化拖慢首屏 IPC；已将 `FilePage` 回归首包（主包 gzip 104.7 KB，仍低于 200 KB 目标），复测可交互耗时与 0.8.5 持平（-1.2%）。

## 六、扫描路径四态对比（管理员实测）

- 脚本：`scripts/bench-scan-paths.ps1`（管理员），四态 = walkdir / native / MFT（强制，`ROOTUP_MFT_FORCE=1`）/ 优化器；语料 1k / 10k / 20k / 30k / 50k，预生成一次、跑完统一清理。
- 一致性：每档四态 discovered 全等、errors=0、MFT 臂确认启用；DB 路径/大小/时间集合 15 对严格对比全部 PASS。

| 规模 | walkdir | native | MFT（强制） | 优化器 |
| --- | --- | --- | --- | --- |
| 1k | 129 ms | 24 ms | 3230 ms | 29 ms |
| 10k | 956 ms | 106 ms | 3111 ms | 102 ms |
| 20k | 1691 ms | 188 ms | 3009 ms | 182 ms |
| 30k | 3920 ms | 430 ms | 3353 ms | 418 ms |
| 50k | 6719 ms | 685 ms | 3761 ms | 765 ms |

- 结论：原生枚举在 50k 内全面胜出（native vs walkdir 1k -81%、10k -89%、50k -90%）；MFT 因全卷 2.6GB 读取固定成本（read_ms ≈ 2.3–2.5s）在小目录反而更慢，本机交叉点在更大规模。优化器在 0.8.6 保持原生是正确且安全的选择；0.8.7 通过持久化模型 + 阈值自动化决定何时切 MFT。
- 结果文件：`benchmarks/results/0.8.6.scan.json`（30 项指标）、`benchmarks/scan-paths-0.8.6.md`、图表 `benchmarks/charts/0.8.6-scan-paths.svg`（已入 README）。
- 附带发现：大目录首次启动时 `notify` 递归监视器注册会遍历整个目录（10k 约 3.9s、20k 约 7.6s），造成启动期短暂无响应；扫描本身不受影响。已记入 0.8.7「启动体验」项。

## 七、遗留风险

- 可交互探针口径与 0.8.7 统一；标签查询收敛待 FTS 评估。
- MFT 优化器当前默认不启用（小语料走原生），符合安全优先路线；四态实测后给出规模阈值结论。
- 大目录首次启动的监视器注册耗时（4–8s）为既有问题，0.8.7 移入延迟服务/后台增量注册；不影响 0.8.6 功能与基准。
- 安装包与 Actions 验证在 push/tag 后执行（第二道保险）。

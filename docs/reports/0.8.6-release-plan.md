# 0.8.6 发布收口执行计划

> 日期：2026-08-10；基线：`9950726`（main，领先 origin/main 45 个提交）；版本：0.8.5 → 0.8.6。
> 目标：以「提交 0.8.6」为终点，完成清理、全量验证、官方基准与性能对比展示、文档与帮助更新、边界与架构审查、0.8.7 对接，最终汇报后由用户批准推送与打标。

## 一、原则

1. 每步原子、可独立验证：单测 → 门禁 → 基准 → 文档 → 提交，逐步推进，任一失败先修复再继续。
2. 性能为本版绝对升级重点：官方基准一次跑完（同机同指纹、确定性语料、多轮取中位数），与 0.8.6-dev（同 OS 25H2）对比为主要 delta；0.8.5 尽量本机复测引擎指标，若不可行则保留历史绝对值并明确标注 OS 差异。
3. 脚本正确性优先：基准脚本必须自检确定性、指纹、样本数与清理结果；不引入新第三方依赖；结果 JSON 只追加不覆盖。
4. 权限边界：官方引擎/系统基准无需管理员；MFT 提权验收此前已由管理员完成并落档，不重复执行。若需复核，单独运行 `scripts/mft-verify.ps1`（管理员）。
5. 发布纪律：门禁全绿 → 边界审查 → 分组提交 → 最终汇报 → **用户批准后才 push main + tag v0.8.6**。

## 三、可比较性规则

- 同机同指纹（os|cpu|rustc|ram_gb）才计算 delta；0.8.6 vs 0.8.6-dev 满足；0.8.5 历史值因 23H2→25H2 变更标注不可直接比较。
- 确定性语料 seed=20260806，`corpus.json` 单源；每次全量前 200 文件 ×2 确定性自检。
- 引擎 5 轮（warmup 2 不计）、系统 7 轮；指标输出 p50/p90/p99/min/max/mean/CV/samples。
- 15% 警示：仅提示，逐项给原因与 0.8.7 去向；churn VACUUM 硬断言（VACUUM 后体积不得大于 churn 后）。

## 四、风险与回退

- v0.8.5 复测编译失败/耗时过长：记录原因，回退历史数据并标注；不阻塞 0.8.6。
- 基准期间环境负载：负载门禁失败即中止，提示用户关闭后台任务后重跑。
- 版本/帮助测试失败：回到 M1 修复后再进 M3。
- push 依赖本机 git 凭据；失败则停在提交阶段汇报。
